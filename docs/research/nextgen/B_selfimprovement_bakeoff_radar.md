# Topic B — Self-improvement and bake-off radar

**Observed 2026-10-01.** “Fit” is 1–5 for one low-cost Hetzner host (15 GB RAM, 28 GB free), GitHub Actions, Persian/RTL factory workloads, and unreliable external access. “UNVERIFIED” means I could not establish the point from a primary source.

## Decision

Build a small, deterministic Roxira evaluation corpus and make it a merge gate before adding evolutionary self-improvement. Use public benchmarks as periodic calibration, not as the production score. Adopt controlled prompt/config optimisation only after the corpus has baseline results. Do not let a system modify its own factory, routing policy, secrets, merge rules, or production deployment configuration automatically.

### The production-credible bake-off

Use a versioned `factory-evals` repository with **12–20 private tracer bullets**, not a public leaderboard:

- 4 Next.js RTL tasks: form validation, accessible modal, Persian number/date rendering, mobile layout.
- 4 NestJS/FastAPI tasks: DTO validation, ownership checks, migration-free repository change, OpenAPI-to-client update.
- 4 delivery tasks: failing-test repair, CI diagnosis, secure configuration change, Playwright flow repair.
- Each task has an immutable base commit, an exact verifier, CPU/RAM/disk/time ceilings, and a secret-free fixture.
- Score only executable evidence first: verifier pass, no test regression, lint/typecheck, E2E pass, elapsed time, tokens, API cost, retries, and agent-policy violations.

Run every candidate **three times with a fixed seed where supported**, publish raw trajectories and container/image hashes, then rank by a Pareto frontier rather than a single blended score. A candidate is eligible only if it beats the incumbent’s median success rate without exceeding its 90th-percentile cost or failure-policy rate.

Do not use a single LLM judge as the acceptance authority. Research continues to show position, verbosity, provenance/self-enhancement, and consistency bias in LLM judging; use blinded random ordering, swap candidate order, a held-out human-labelled calibration set, and executable checks for all objective outcomes. [Bias study](https://doi.org/10.48550/arXiv.2410.02736), [FairJudge paper](https://proceedings.mlr.press/v306/yang26n.html). Seen 2026-10-01. **Fit 5/5; cost near-zero for deterministic checks. Verdict: ADOPT.** First task: create 20 paired outputs where a judge must prefer a known-correct result, then fail CI if judge agreement drops below the agreed baseline.

| **AlphaEvolve-style search** | Google DeepMind’s internal evolutionary coding agent combines LLM proposal generation with automated evaluators; Google reports deployments in data-center, chip-design, and training optimisation. Seen 2026-10-01. | Service/system availability and license: **UNVERIFIED as a reusable product**; **fit 1/5**. Its credible use case is a tight, cheap, deterministic optimiser—not arbitrary software delivery. | **SKIP implementation.** Adopt only the pattern: many cheap proposals, deterministic evaluator, archive, held-out replay, and strict budget. First task: optimise a pure function or CI-cache policy with a test oracle, not agent code. |
| **Agent-config evolution** | The practical subset of evolutionary search: mutate prompts, tool descriptions, model choice, timeouts, and retry policies; evaluate against a fixed corpus. GEPA explicitly supports prompts, code, agent architectures, and configurations. [GEPA](https://github.com/gepa-ai/gepa). Seen 2026-10-01. | MIT for GEPA; **fit 5/5** if changes are reviewable data, not live self-editing. Cost is an explicit per-experiment model budget. | **ADOPT after baseline.** Encode the agent configuration as versioned JSON/YAML; test 10 bounded variants on five training tasks and replay the winner on five hidden tasks before opening a PR. |

**Credibility line:** DSPy/GEPA plus a good local evaluator is production-credible. DGM and AlphaEvolve are valuable research patterns, not permission to run recursive self-modification in a delivery pipeline. Optimising a weak or contaminated score merely produces a more efficient way to game it.

| **Model tournaments** | A repeatable internal protocol, not a vendor benchmark: identical task/base commit/tool policy, blind candidate labels, three runs each, success/cost/latency distribution, and a holdout replay before promotion. Source basis: [SWE-bench-Live protocol](https://github.com/microsoft/SWE-bench-Live) and [RouteLLM calibration warning](https://github.com/lm-sys/RouteLLM). Seen 2026-10-01. | Roxira-owned; **fit 5/5**; model-call cost only. | **ADOPT.** Run a monthly tournament: one strong paid candidate, two cheap candidates, and current champion across the 12-task corpus; promote only with a predeclared margin. |

Use two CI levels:

1. **PR smoke gate:** 3–5 deterministic tasks, full test/typecheck/E2E, maximum cost and time; blocks merge.
2. **Nightly tournament:** full private corpus, three trials, fresh sandbox, cost report, human review for a proposed policy/model/config change.

A regression is not just lower success: it includes increased retries, wall time, token cost, test flakiness, unsafe command attempts, secret exposure, or worse Persian/RTL acceptance cases.

Implement the radar as a low-risk pipeline: **ingest → canonicalise/deduplicate → score metadata locally → require primary source → human review → append decision log**. It should recommend a trial, never install software, create credentials, or alter production.

## Ranked top-8 adoption list

1. **Private tracer-bullet corpus plus deterministic PR smoke gate** — first create 12 replayable tasks and a JSON score schema.
2. **Monthly blinded model/agent tournament** — three trials, fixed envelope, hidden holdout replay, cost and safety metrics.
3. **Promptfoo GitHub Action** — add a five-case PR evaluation with an explicit spend cap.
4. **DSPy + GEPA for one bounded, non-production prompt** — human-reviewed train/holdout split; promote via PR only.
5. **GitHub + HN + arXiv tech radar** — daily metadata ingestion and a weekly human-ranked shortlist.
6. **SWE-bench-Live two-task calibration** — validate language breadth on disposable GitHub runners.
7. **RouteLLM-style measured escalation policy** — log 200 task envelopes, then compare against fixed cheap-first routing.
8. **Inspect AI base-package trial** — one custom evaluation and log viewer; avoid the full 35-GB eval installation.
